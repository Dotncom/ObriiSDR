# Окремий модуль Reticulum

Стан: версія 0.2.0 з ефірним форматом RNode, окрема від Obrii SDR та конструктора Mesh/MANET.
Модуль використовує **офіційний `rns==1.5.5`** для ідентичностей, підписаних
announce, маршрутизації, шифрування, proofs, Links та request/response.
Власний код відповідає за керування процесом, радіочергу, фрагментацію і LoRa IQ.
Це також самостійний модуль. Інтеграція в Obrii 8.1 описана окремо в
`mesh_protocol_adapters.md` та `mesh_hybrid_ports.md`; вона запускає окремий
локально налаштований RNS-процес, не завантажує його в гарячий RX-тракт.

## Склад

| Компонент | Файл / ціль | Призначення |
|---|---|---|
| RNS-вузол | `src/reticulum/obrii_reticulum/node.py` | Один RNS у власному процесі; постійна identity; destination `obrii.mesh` |
| Пакетний інтерфейс | `transport.py` | Керована хостом черга TX, RX, offline/reconnect, статистика |
| Фрагментація OBRN | `fragments.py` | Непрозорий пакет RNS до 564 байтів → LoRa-фрагменти до 255 байтів |
| Ефір RNode | `rnode.py` | Пакет RNS до 508 байтів → один/два LoRa-пакети з заголовком RNode |
| Доступ до мережі | `access.py` | Необов'язкові назва/пароль/розмір IFAC через офіційний RNS |
| API вузла | `service.py` | Обмежені JSON Lines через stdin/stdout без мережевого RPC-порту |
| Python-клієнт | `client.py` / `SidecarClient` | Запуск, команди, тайм-аути, завершення власного дочірнього процесу |
| C++17 bearer | `lora/reticulumlora.h`, `ObriiReticulumLoRa` | TX: фрагмент → IQ; RX: потік IQ → фрагмент із перевіреним LoRa CRC |

RNS має глобальний стан процесу. Конструктор повинен запускати **один sidecar
на вузол**, з окремим каталогом стану. Кожен вузол підтримує 1–8 інтерфейсів.
`--transport` вмикає роль маршрутизатора; звичайні вузли не пересилають чужий трафік.
Вузол не відкриває SDR, LAN/serial-інтерфейси або загальний екземпляр RNS.
Стан у `~/.reticulum` не використовується. Каталог блокується ОС від одночасного
використання двома процесами; після аварійного завершення блокування знімається ОС.

## Збірка та запуск

Windows, Python 3.12, CMake і MSVC 2022:

```powershell
.\tools\build_reticulum_module.ps1 -Test
```

Скрипт створює ізольоване оточення `build/reticulum-venv`, встановлює закріплені
залежності, збирає `build/reticulum/Release/ObriiReticulumLoRa.lib` та перевіряє
Python/API і наскрізний обмін через C++ LoRa-модем. Глобальний Python не змінюється.
`requirements-lock.txt` фіксує перевірене оточення Windows x64 / Python 3.12.
Поточний адаптер навмисно відхиляє іншу версію RNS: він використовує також
внутрішній API `_add_interface`, який слід повторно перевіряти при оновленні RNS.

Ручний запуск:

```powershell
$env:PYTHONPATH = (Resolve-Path src/reticulum).Path
& build/reticulum-venv/Scripts/python.exe -u -m obrii_reticulum.service `
    --state-dir build/reticulum-nodes/node-a --interface lora0 --mtu 255 --bitrate 1100
```

`--interface` можна повторити. Імена: 1–32 ASCII-символи `[A-Za-z0-9_.-]`.
`--bitrate` — оцінка корисної швидкості пакетного транспорту в біт/с для таймерів RNS,
а не частота дискретизації. Підбирати з урахуванням SF/BW/CR, фрагментації та пауз.
Роль transport, MTU, bitrate, framing і список інтерфейсів задаються при запуску.
`--framing obrn` — попередній режим за замовчуванням; `--framing rnode` —
сумісне пакування RNode на всіх радіоінтерфейсах вузла. RNode потребує `--mtu 255`.
Зміна ролі або framing через перезапуск зберігає identity і destination.
`status.interfaces[].framing` повідомляє обраний режим.

Власний `config` створюється атомарно; чужий або вручну змінений конфіг не
перезаписується. Пошкоджений файл identity спричиняє помилку, а не зміну адреси.
Каталог містить приватні ключі: він має залишатися локальними даними вузла,
поза бібліотекою загальнодоступних пресетів та Git. На Windows права успадковуються
від каталогу користувача; на POSIX нові каталоги/identity створюються з 0700/0600.

## JSON Lines API v1

Один UTF-8 JSON-об'єкт з `\n` на команду. Максимум 32768 байтів на рядок.
`id` необов'язковий, рядок до 64 символів; відповідь повертає той самий `id`.
`status.protocol_version=1` позначає версію цього RPC.
Невідомі операції та аргументи відхиляються. Немає shell-команд або довільного
виконання коду. Бінарні дані — строгий стандартний base64; хеші адрес/Links —
32 hex-символи, хеші пакетів — 64. stdout містить лише відповіді RPC.

```json
{"id":"1","op":"status"}
{"id":"1","ok":true,"result":{"adapter_version":"0.2.0","...":"..."}}
{"id":"2","op":"poll_tx","interface":"lora0","busy":false}
{"id":"2","ok":true,"result":{"tx":{"ticket":1,"data":"...base64..."}}}
{"id":"3","op":"tx_done","interface":"lora0","ticket":1,"sent":true}
{"id":"4","op":"rx","interface":"lora0","data":"...base64..."}
{"id":"5","op":"events","limit":128}
```

Об'єкт status у прикладі скорочено. Помилки мають форму
`{"id":"...","ok":false,"error":"..."}`. Пошкоджений надмірний або
незавершений рядок завершує процес, щоб хвіст не став іншою командою.

| `op` | Додаткові аргументи | Результат / дія |
|---|---|---|
| `status` | — | Identity, destination, public key, роль, peers, Links, черги і лічильники |
| `events` | `limit` 1..256, типово 128 | Забрати накопичені події |
| `announce` | `data` base64, до 128 байтів, необов'язково | Поставити підписаний announce у транспорт |
| `request_path` | `destination` | Запитати маршрут RNS; його поява асинхронна |
| `path` | `destination` | `known`, `hops` |
| `send` | `destination`, `data`, опційно `expected_identity` | Зашифрований SINGLE-пакет 1..383 байти; повертає `packet` |
| `link_open` | `destination`, опційно `expected_identity` | Встановити Link; повертає `link`, готовність через подію |
| `link_send` | `link`, `data` | Пакет 1..MDU активного Link (`status.links[].mdu` / `link_active.mdu`); повертає `packet` |
| `request_echo` | `link`, `data` до 4096 байтів | Обмежений тестовий сервіс `/obrii/echo`; повертає `request` |
| `link_close` | `link` | Завершити Link |
| `poll_tx` | опційно `interface`, `busy` | Один фрагмент з `ticket` або `tx:null` |
| `tx_done` | `ticket`, `sent` boolean, опційно `interface` | Підтвердити/відхилити фактичну передачу фрагмента |
| `rx` | `data`, опційно `interface` | Фрагмент; `packet_complete` повідомляє лише завершення складання |
| `online` | `online` boolean, опційно `interface` | Вимкнути/відновити інтерфейс; вимкнення очищує чергу і складання |
| `discontinuity` | опційно `interface` | Скинути незавершене складання після розриву потоку |
| `shutdown` | — | Відповісти та штатно зберегти/завершити RNS |

Типовий інтерфейс — `lora0`. `expected_identity` — очікуваний fingerprint
публічної ідентичності, отриманий довіреним способом. Він перевіряється перед
відправленням/відкриттям Link; одного імені вузла для перевірки недостатньо.
Відправлення потребує перевіреного announce і маршруту до destination `obrii.mesh`.

Основні події: `announce`, `packet_received`, `delivered`, `delivery_failed`,
`link_active`, `peer_identified`, `link_data`, `link_closed`, `response`,
`request_failed`, `interface_state`, `tx_rejected`, `tx_failed`.
`packet_received` та `link_data` містять `data` у base64; receipt-події — `packet`;
відповідь містить `request`, `link`, `data`.

**SINGLE шифрує дані для одержувача, але не автентифікує відправника.**
Тому `packet_received.sender_authenticated=false`. Ініціатор Link автоматично
ідентифікується власною RNS identity. На стороні одержувача автентифікація стає
доступною після `peer_identified`; `link_data` окремо містить `peer_identity` та
`sender_authenticated`. Це криптографічна ідентичність, не адміністративні права.
`delivered` означає перевірений RNS proof, а не підтвердження виконання прикладної дії.
`packet_complete` та `tx_done` такого підтвердження не дають.

Черга: 32 цілі RNS-пакети на інтерфейс, один виданий TX ticket за раз.
При переповненні відхиляється цілий новий пакет (`tx_rejected`). `sent=false`
видаляє решту фрагментів його пакета (`tx_failed`), без автоматичного RF-повтору.
Незавершений ticket не має прихованого тайм-ауту: хост обов'язково завершує його
або переводить інтерфейс offline. Старі ticket після offline відхиляються.
Готовність `send` означає прийняття RNS, а не успіх радіопередачі: потрібно читати
події і стежити за чергами. До 128 очікуваних proofs, 32 Links, 16 запитів,
256 peers, 256 подій (найстаріші витісняються, `dropped_events` рахує втрати).

## Стикування з LoRa та конструктором

1. Конструктор запускає sidecar для кожного вузла та зберігає його публічні адреси.
2. На кожен радіоінтерфейс хост створює `obrii::reticulum::LoRaBearer`.
3. Коли канал дозволяє TX, хост викликає `poll_tx`, декодує base64 та передає байти
   в `bearer.modulate(frame)`. `sampleRate()` і `timeOnAirSeconds(frame)` доступні.
4. Після завершення передачі IQ викликає `tx_done(sent=true)`; при збої — `false`.
5. Прийняті блоки IQ надходять у `bearer.receive(...)`; кожен повернутий `RadioFrame.data`
   без змін передається в `rx`. Події читаються окремо через `events`.
6. При розриві IQ, зміні частоти/дискретизації або offline потрібно викликати
   `bearer.reset()` та `discontinuity`/`online(false)` для відповідного інтерфейсу.
   Нові PHY-параметри застосовуються створенням bearer з новою конфігурацією.

Типова PHY режиму OBRN: SF11, BW250 кГц, CR4/5, preamble16, oversampling2, sync word **0x12**,
explicit header, payload CRC. Це окрема мережа від типового Meshtastic sync0x2b.
SF/BW/CR/sync/IQ inversion і frame MTU мають збігатися на сторонах радіоканалу.
Sync word не є ключем доступу. C++ bearer перевіряє LoRa CRC і базовий префікс;
повну структуру, довжини та CRC32 фрагментів OBRN перевіряє Python reassembler.
Для RNode обов'язково вибирати відповідний PHY-профіль, описаний нижче.

Хост відповідає за частоту, рівні, half-duplex, CAD/backoff, airtime, дозволений
режим передавання і доставку віртуального IQ між вузлами. Видача фрагмента з
`poll_tx` **не запускає RF**. LoRaBearer не виконує I/O і не керує SDR.
Для C++/Qt достатньо запустити процес через QProcess, реалізувати таблицю JSON-команд
і приєднати ціль `ObriiReticulumLoRa`; Python `SidecarClient` показує той самий цикл.

```python
from obrii_reticulum.client import SidecarClient

with SidecarClient(python_exe, state_directory, transport=True) as node:
    addresses = node.initial_status
    node.call("announce")
    tx = node.call("poll_tx", interface="lora0", busy=False)["tx"]
    # Host delivers tx["data"] through its PHY; then reports tx_done.
```

Власний CMake підключається через `add_subdirectory(src/reticulum)` і
`target_link_libraries(host PRIVATE ObriiReticulumLoRa)`. Qt не потрібний модулю.
Sidecar вимагає Python та встановлений офіційний RNS; сама C++ бібліотека
не містить RNS і не замінює його Python runtime.

## Ефірний формат RNode

Реалізований нормальний пакетний режим офіційної **RNode Firmware 1.86**;
еталон — commit `56775c51b60a6190242e324c210997dcc7637e53`.
SDR передає ті самі байти LoRa-пакетів, які очікує RNode. На боці існуючого
пристрою лишається штатна прошивка та звичайний RNS-хост із RNodeInterface.

```powershell
$env:PYTHONPATH = (Resolve-Path src/reticulum).Path
& build/reticulum-venv/Scripts/python.exe -u -m obrii_reticulum.service `
    --state-dir build/reticulum-nodes/rnode-a --framing rnode --mtu 255 --bitrate 1000
```

Python-клієнт має параметри `framing="rnode"` та опційний `access_file=...`.
Нативний хост створює профіль після вибору SF/BW/CR:

```cpp
obrii::lora::Config phy;
phy.spreadingFactor = 11;
phy.bandwidthHz = 250000;
phy.codingRate = 1; // 4/5; у налаштуваннях RNode це codingrate=5.
auto config = obrii::reticulum::RadioConfig::rnode(
    phy, obrii::reticulum::RNodeModem::Sx127x);
obrii::reticulum::LoRaBearer radio(config);
```

Для SX1262/SX1268 є `RNodeModem::Sx126x`. Профіль застосовує sync0x12
(відповідник регістрів SX126x 0x1424), normal IQ, explicit header і LoRa CRC.
Преамбула обчислюється за правилами прошивки: ціль 24 мс, мінімум 18 логічних
символів; SX127x записує на чотири символи менше в радіорегістр. За типових
SF11/BW250 фізичне значення `phy.preambleSymbols` дорівнює 14 для SX127x та 18
для SX126x. На SF7/BW250 це 43 та 47 відповідно. RX перевірено в обох напрямках
між профілями з різною довжиною преамбули.

LDRO теж відповідає драйверам RNode: цілочисельна тривалість символу у мс має
перевищувати 16. На межі 16.384 мс (SF9/BW31.25, SF10/BW62.5, SF11/BW125,
SF12/BW250) це **LDRO Off**, хоча загальний профіль LoRa Auto обрав би On.
Після зміни SF/BW/CR потрібно знову викликати `RadioConfig::rnode(...)`.
Інші прошивки/форки можуть мати інші правила PHY; фактичні налаштування мережі
мають збігатися з обраним профілем.

Формат LoRa payload: один байт заголовка, потім дані RNS. Біти 7..4 — випадковий
4-бітний sequence; bit0 — SPLIT. До 254 байтів RNS передаються одним кадром,
255..508 — двома кадрами по максимум 254 байти даних. Обидва мають однаковий
заголовок з SPLIT=1. Обгортка OBRN та KISS-escaping **не додаються в ефір RNode**.
При рівно 508 байтах upstream TX додатково випускає порожній split-заголовок;
наш RX ігнорує його, а наш TX надсилає лише дві заповнені частини. Еталонний RX
прошивки підтвердив, що цього достатньо для отримання всіх 508 байтів.

У RNode немає part index, повної довжини, sender ID або CRC32 у цьому заголовку.
Частини збираються в порядку надходження, по одному незавершеному пакету на радіо.
Ідентичні повні частини можуть бути коректними, тому їх не можна відкидати як
повтори. При втраті/перестановці/колізії sequence транспорт не гарантує складання;
захист цілісності та proofs залишаються на рівні RNS. Неповний пакет має TTL120 с,
зміна sequence або одиночний пакет перериває попереднє складання. Короткий
осиротілий хвіст відхиляється. Лічильник `rx_empty_frames` показує порожні трейлери.
Черга хоста видає дві частини послідовно; хост має зберігати цей порядок у RF.

RNode-інтерфейс має HW_MTU508 і використовує звичайний RNS MTU500, як офіційний
RNodeInterface; підвищення Link MTU з режиму OBRN тут не застосовується.
Для роботи потрібні однакові частота, SF/BW/CR, PHY-профіль і IFAC-параметри.
Підтримується поточний діапазон нашого PHY: SF7..12, BW31.25/62.5/125/250/500 кГц,
CR4/5..4/8. SF5/6, вузькі BW та SX1280/2.4 ГГц поки потребують розширення LoRa PHY.
Promiscuous/implicit-режим та USB/BLE/TCP-керування самим RNode не входять до
цього ефірного адаптера. Прикладний endpoint лишається `obrii.mesh`; LXMF/Sideband
потребують свого прикладного модуля поверх сумісного транспорту.

### IFAC для існуючих мереж

Доступ виконує офіційний RNS через його штатний IFAC. Передати локальний файл
`--access-file PATH` з налаштуваннями на кожен потрібний інтерфейс:

```json
{
  "lora0": {
    "network_name": "example-network",
    "passphrase": "replace-with-network-passphrase",
    "ifac_size_bits": 64
  }
}
```

Назва або пароль можуть бути відсутні. Без файлу інтерфейс відкритий, без IFAC.
Параметри мають точно відповідати `network_name`, `passphrase` та `ifac_size`
штатного конфігу RNS; назва сама по собі не є секретним ключем.
Для RNode допустимий IFAC 8..64 біт, кратний 8 (типово 64); 508 байтів вміщують
RNS500 та IFAC до 8 байтів. OBRN допускає до 512 біт у межах свого HW_MTU564.
Назва/пароль до 1024 UTF-8 байтів; файл до 64 КіБ; невідомі поля відхиляються.
RPC повертає лише `ifac_enabled` і `ifac_size_bits`, без мережевих секретів.
У командному рядку процесу передається шлях до файлу, а не пароль. Файл є локальними
закритими даними разом з identity; загальнодоступний пресет конструктора має
містити посилання на локальні облікові дані, а не їхній вміст.

## Формат фрагмента OBRN v1

Це **власний радіоконверт Obrii**, не формат ефіру RNode. Нативні RNode/Meshtastic/
LoRaWAN-пристрої не зможуть декодувати його як свою радіомережу. Усередині —
незмінений офіційний пакет RNS, тому вузол може маршрутизувати його іншими
інтерфейсами RNS у майбутньому. Для сумісності з ефіром RNode вибирати `--framing rnode`.

Усі багатобайтові числа big-endian. Заголовок 22 байти:

| Offset | Байти | Поле |
|---|---|---|
| 0 | 4 | ASCII `OBRN` |
| 4 | 1 | version=1 |
| 5 | 1 | count |
| 6 | 8 | datagram ID: випадковий 32-bit session prefix + 32-bit counter |
| 14 | 2 | index з 0 |
| 16 | 2 | total length 1..564 |
| 18 | 4 | CRC32 цілого пакета RNS (`zlib.crc32`) |
| 22 | N | Частина пакета |

Місткість фрагмента = MTU−22; MTU задається 64..255 (типово 255).
Count і довжини обчислюються однозначно; ніяких довільних великих allocations
з полів заголовка. RNS MTU за замовчуванням 500, інтерфейс допускає до 564 байтів
для запасу заголовків/узгодженого link MTU. При MTU255 це максимум три фрагменти.
Приймаються перестановки; повтори і неузгоджені фрагменти відсіюються. Обмеження:
64 незавершені пакети, 128 недавніх ID, TTL120 с; прострочення перевіряється при
новому RX. CRC32 виявляє пошкодження, але не є автентифікацією. Короткий кеш ID
також не замінює криптографічні перевірки та дедуплікацію RNS.

## Перевірки та межі версії

Тести охоплюють усі довжини 1..564 при MTU64/128/255, незалежний вектор заголовка,
перестановки/повтори/CRC/TTL/ліміти, 5000 випадкових некоректних фрагментів,
чергу та stale tickets, збереження identity, блокування каталогу, чужий конфіг,
пошкоджений ключ, строгі RPC-аргументи і надмірний рядок.

Наскрізна топологія A ↔ B ↔ C не має прямого каналу A–C. B — єдиний маршрутизатор
з одним спільним радіоінтерфейсом. Перевіряються announce, маршрут мінімум у два
хопи, SINGLE з 383 байтами, proof, Link, ідентифікація, link data на межі MDU,
echo з 4096 байтами даних, які не стискаються, відмова TX під час offline,
відновлення обміну без перезапуску та закриття Link.
Окремий прогін пропускає **кожен фрагмент** через C++ LoRa-модулятор
і streaming receiver. Для швидкості тест використовує SF7 і завищену віртуальну
bitrate; це перевірка коректності обміну, не оцінка продуктивності реального ефіру.
Нативний тест додатково перевіряє SF11, профілі SX127x/SX126x, порогові режими LDRO
і збіг airtime з кількістю IQ-відліків. Та сама наскрізна топологія перевірена
в режимі RNode без IFAC та з IFAC, включно з IQ. Окремо перевірено відхилення
пакетів з неправильним IFAC.

Сумісність байтового формату підтверджено **8128** випадками: усі довжини 1..508
та всі 16 sequence, у двох напрямках проти скомпільованих незмінених функцій
`transmit` / `receive_callback` офіційної прошивки. Для offline-тестів збережено
44 граничних вектори з commit/hash provenance. Повне повторне порівняння:

```powershell
& build/reticulum-venv/Scripts/python.exe tools/generate_rnode_vectors.py --download
```

Скрипт завантажує закріплені SHA256 файли лише в ігнорований `build/rnode-reference`,
зберігає GPL-повідомлення та збирає окремий еталонний EXE. За наявності кешу можна
запускати без `--download`. Цей EXE не лінкується у production-модуль і не входить
до його install. Звичайний `build_reticulum_module.ps1 -Test` використовує збережені
вектори без завантаження прошивки або підключеного RNode. Після встановлення
Python-залежностей самі тести можуть працювати без інтернету.

Поки не під'єднано GUI/конструктор, віртуальний IQ hub, SDR або реальні RNode.
Не реалізовані LXMF, GUI чат, файловий API Resource, збереження прикладної історії
та віддалене адміністрування. Echo використовує штатний механізм Resource для
довгих запитів/відповідей, але публічний API обмежує дані 4 КіБ й не відкриває
загальний прийом файлів. Розширення прикладних сервісів може використовувати
той самий RNS Link без зміни PHY/framing.

RNS працює за реальним системним часом. Прискорений/призупинений час симулятора
потрібно окремо узгодити; поточний sidecar не підміняє годинник RNS.
Фізична сумісність RF, колізії та повільні реальні LoRa-маршрути ще потребують
апаратних/тривалих випробувань після інтеграції. Потоковий LoRa RX успадковує
обмеження модуля PHY, описані в `docs/lora_phy.md`.
